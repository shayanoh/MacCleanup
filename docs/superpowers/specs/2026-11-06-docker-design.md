# MacCleanup: Docker screen (milestone 3) design

Status: draft for approval, 2026-11-06. Parent designs: `2026-11-06-maccleanup-design.md` and `2026-11-06-caches-projects-design.md` (whose sections 4, 4a, 7, 8 and 11 and the rules in `CLAUDE.md` apply unchanged). Convention as in the parents: **[User]** = decided by the user, **[My call]** = decided by the author, open to change.

## 1. Intent and why

Docker Desktop on this Mac keeps everything inside one sparse VM disk file, `~/Library/Containers/com.docker.docker/Data/vms/0/data/Docker.raw` (32 GB on disk today, 466 GB logical maximum). Two things hurt:

1. Docker's own tooling is cryptic: IDs, truncated commands, no single view of what is connected to what, no last-used dates. The user wants to see images, containers, volumes and build cache with their relationships, dates and costs, without learning commands. **[User]**
2. Deleting things inside Docker does not shrink `Docker.raw`. The space comes back to the Mac only after a trim of the VM disk. The user does this today with `docker run --privileged --pid=host docker/desktop-reclaim-space`. **[User]**

The screen is also a debugging aid: for any image or build-cache record it shows each layer, what that layer costs, and the command that made it, so the user can see why an image is big. **[User]**

Success: the user opens the page and understands in a minute what each image, container, volume and cache record is, what uses it, what deleting it frees inside Docker, and how much of that really comes back to the Mac afterwards, confirmed by measured numbers. **[User]** (spirit)

## 2. Goals

- G1. A new sidebar page **Docker** (replaces the dimmed Docker entry; its digit key is its position in `SIDEBAR` as always). **[User]**
- G2. One list, no tabs inside the page, drawn like Caches & Projects: totals line, status line, filter box, coloured section bands (**IMAGES**, **VOLUMES**, **BUILD CACHE**, plus **CONTAINERS** that are not shown under an image, see G3), bold group lines, Explorer-style columns, scrollbar with `a/b` position, graph pane (treemap default, `g`, `[`, `]`) over a Details pane. **[User]** ("B is better, no tabs, follow the caches page and explorer"). Mockup: `.superpowers/brainstorm/35834-1793991943/content/docker-screen-v2.html` (local, not committed).
- G3. Show what is connected to what as a tree: an image holds the containers created from it, a container holds the volumes it mounts. Anything with no holder is labelled (unused image, dangling image with no tag, volume used by no container). Where one thing is held by two parents (a volume shared by two containers, an image that is the base of another), it is listed under its first parent in a stable order and the Details pane lists every holder. **[My call]** on the exact tree shape; the connectivity itself is **[User]**.
- G4. Columns: Name, Size, Frees, Last used, Created, in the Explorer's style (sort arrow on the active header, share bar hidden first when narrow). Docker has one size notion, so there is no separate "On disk" column. The `s` sort cycle follows the header order. **[My call]** The two date columns are added to the Explorer too in the same change (the consistency rule in `CLAUDE.md`), with the dates being the entry's modification time there; README key table and tests change together.
- G5. **Layers and build steps.** An image expands to its layers; a build-cache record shows the step it came from. Each shows the command that produced it, its size, whether it is shared with other images or cache records or only used by this one, and the biggest layer is marked. **[User]**
- G6. **Accurate numbers computed by the app.** Docker's own "unique size" is wrong on this Mac (it reports `-5.365e+07B` for `nginx`), so shared, unique and frees are computed from layer/blob identity: Frees of an image is what is left after removing it (its layers not used by any other image or cache record that stays), and the set-wise rule of the parents applies: what a whole selection frees is computed over the union of the marks (a layer shared by two marked images frees once everything holding it is marked). **[User]** (spirit) / **[My call]** (mechanism).
- G7. **Last used and Modified.** Build-cache records have a real last-used time from Docker. Docker does not record when an image or volume was last used; show the best available proxy and say which it is in the Details pane: for an image, the newest creation/start/finish time among its containers, else its creation/tag time; for a volume, the same over the containers that mounted it, else its creation time. **[My call]** (proxy) / **[User]** (wants the dates).
- G8. **Read-only browsing** of the inside of images, containers and volumes: `Enter` on one opens a file tree (folders with sizes where cheaply known, file modification times). Nothing in it can be edited, deleted or marked. A volume is browsed through a short-lived helper container with the volume mounted read-only (and no network); an image or container is browsed from a created-but-never-started container's filesystem. Helpers are labelled so they are recognisable and are always removed, including after errors and on quit. **[User]** (browse images/containers/volumes read-only) / **[My call]** (mechanism).
- G9. **Deleting** goes through the one shared selection and the one review (`App::marks`' successors, parent section 4a): Docker items become new entry kinds in the same selection, shown in the same review, and `d` on any screen reviews everything marked. Removal is done through Docker's own commands (`docker image rm`, `docker container rm`, `docker volume rm`, build-cache pruning by record), never by touching files in `Docker.raw`. **[User]** (existing rule: docker is cleaned through its own commands)
- G10. **Reclaim the VM disk.** After any review that removed Docker items, the app runs the trim (`fstrim` inside the Docker VM, the same effect as `docker run --privileged --pid=host docker/desktop-reclaim-space`), waits until it exits, measures `Docker.raw` on disk (`du`-style allocated size, not the apparent size) before and after, and reports "VM disk shrank by X", counted as truly freed. It also exists as a row the user can mark and run on its own, any time, with no other Docker item marked. **[User]** ("both: run after every delete, and a row I can run myself")
- G11. A status line shows the Docker connection (CLI found, daemon reachable, which context), and the VM disk: `Docker.raw` allocated size versus what Docker reports in use, so the user sees how much sits unreclaimed. **[User]** (extra space after removing things) / **[My call]** (wording)

## 3. Non-goals and anti-goals

- No starting, stopping, building, pulling, running, editing, renaming or tagging anything. The page only reads, browses (read-only) and deletes. **[User]**
- No deleting by path, ever. No removal of anything a running container holds (the CLI refuses; the app also refuses before asking). **[My call]**
- Anti-goal: a "frees" number that over-promises. Freed inside Docker is not freed on the Mac until the trim has run; both numbers are shown and named, and the finish screen uses the measured one. **[User]** (spirit of parent section 12)
- Not in this release: remote or non-default Docker contexts, Docker engines other than Docker Desktop on this Mac (Colima, OrbStack, Podman) beyond showing the page's "Docker not available" state; compacting `Docker.raw` by shutting Docker down; network, plugin, Compose-project and Docker Hub views. **[My call]**
- Anti-goal: leaving helper containers or images behind. **[My call]**
- Never escalate privileges on the Mac or ask for a password. The trim runs as root inside Docker's VM, not on macOS; it is still shown in the review as a command with its exact text. **[My call]**

## 4. Constraints (inherited rules that matter most here)

- Rust, ratatui 0.30, crates only via `cargo add`; format, clippy clean (`CLAUDE.md`).
- Nothing slow on the UI thread. Docker calls (listing, inspecting layers, history, browsing) run on background threads through `bg::Latest`/`bg::Work`; a caller that can fire every tick never starts a new job while one is pending. **[inherited]**
- Commands run through the existing `CommandRunner`/`RunControl` machinery: absolute program path of one exact install, home folder as `cwd`, no stdin, timeout, own process group, cancel switch (`Esc`; `q`/`Ctrl-C` cancel and quit), live last output line and elapsed time. Never add `--force` on the user's behalf. Real Docker commands are never run in tests: `FakeRunner` or a no-op runner, and listings are tested from recorded JSON fixtures. **[inherited]**
- A review containing commands is confirmed only by `y`; folder moves first, then commands in the listed order; a failing command neither stops the rest nor undoes anything. Marking a group or section never marks a command-style row that removes things irreversibly (decide per kind below). **[inherited]**
- Everything shown goes through `ui::clean`/`fit`/`fit_start`; ASCII fallback and `--no-animation` as everywhere; dialogs grow in as everywhere.
- Update `CLAUDE.md` (code map, rules, key table) and `README.md` in the same change; the sidebar digit table changes.

## 5. Decisions about marking and deleting

- Docker removals are irreversible (no ToBeDeleted equivalent). They are therefore command-style entries in the shared selection, shown with their exact command, and need `y`. Bulk marks (group, section) mark **only** things that are safe to take in bulk: dangling images and build-cache records not used by any image. Everything else is marked one row at a time. **[My call]** (extends the existing "bulk marks skip command rows" rule)
- Images used by a running container cannot be marked (dimmed, with the reason in Details); volumes used by any container (running or stopped) are marked only on their own and carry a warning in the review that data in them is lost for good. **[My call]**
- Volumes can hold databases: they are always shown amber, never green, and the review lists them under a heading saying the data cannot be recovered. **[My call]**
- Removing a tagged image removes the tag and layers nothing else holds; the review lists what stays because something else holds it. **[My call]**
- The VM-disk reclaim row (G10) is a command row at the top of the page. It is marked like any command row, appears in the review with the exact command, and shows "frees up to X" (the gap between `Docker.raw` allocated and in use), as an upper bound like the other tool commands. After a review that removed Docker items it is added automatically as the last command, listed in the review so the user sees it and confirms it with the rest (one `y`); a failed trim is reported and does not undo the removals. **[User]** (both, always run after delete) / **[My call]** (listed and confirmed in the same review, not silent)
- After a Docker cleanup, `App::process_refresh` rebuilds the Docker list (a build only counts as current if the list epoch did not change since it started), and `Accounting` records free space before vs after on the Mac volume, with the `Docker.raw` change shown next to it.

## 6. Data sources (to be verified by the builder against current Docker docs, not from memory)

Docker is driven through its CLI (found like the pnpm/npm installs: `PATH`, standard Docker Desktop locations, every install counted once) with JSON output; no Docker API socket client is required. This Mac runs Docker Desktop 4.98.0 (Engine 29.9.2) with the containerd image store (`io.containerd.snapshotter.v1`, overlayfs), which changes how layer and size information is exposed, so layer identity and sizes must be checked against this setup and against the classic store. What the screen needs: images (id, tags, created, size, parent/layer digests), per-image history (layer command, size), containers (state, created/started/finished, image, mounts), volumes (name, driver, size, mountpoint, usage links, created), and build-cache records (id, type, size, created, last used, usage count, shared, description/step command). Where Docker cannot say something (image last used), the proxy rules in G7 apply.

## 7. Left to the builder

- Module layout (a `catalog/docker.rs` or `docker/` module, parsing into an in-memory model; a `ui/docker.rs` screen; how Docker items map onto `scan::Row`/`TRow`-like rows and the shared selection), naming of new entry kinds, how the trim runs inside the VM and how the helper for volume browsing is created, how the browse view reuses the Explorer's list/filter/graph code.
- Exact CLI invocations and JSON parsing, handling of both image stores, timeouts, large outputs.
- Key choices not named above, colours of the section bands, wording, the exact tree ordering and tie-breaks.
- Test plan, with emphasis on: JSON fixtures for both image stores, the shared/unique/frees identity (frees + kept-by-others = footprint) including a layer shared by two marked images, tree building with shared volumes and base images, bulk-mark exclusions, the review text for each command kind, refusing in-use items, helper-container cleanup on error, the trim measurement before/after using a fake `du`, and the Explorer-consistency rule (column order, sort cycle, new date columns in both screens).

## 8. Facts recorded while shaping this design

- `docker/desktop-reclaim-space` is a 149 kB image whose whole entrypoint is `nsenter1 /sbin/fstrim /var/lib/docker`. A test run on 2026-11-06 took 9 s, exited 0 and changed `Docker.raw` allocated size by +100 KB (33,231,512 KB to 33,231,612 KB), because the VM had no freed blocks to give back (about 25 GB images + 4 GB volumes + 5.6 GB build cache is roughly the 32 GB file). It has not yet been shown to shrink the file after a large delete; a throwaway pull/delete/measure test is still open and should be part of the builder's verification.
- On this Mac Docker's reported "unique size" for `nginx:latest` is negative; the app must not trust it.

## 9. Calls made after the builder check (all **[My call]**, open to change)

1. **The automatic trim is a real entry.** When any Docker removal is marked, a "Shrink VM disk" command entry is added to the shared selection automatically, as the last Docker command in the review. It is visible on the page and the user can unmark it (then the removals run without a trim). It always runs after every Docker removal in that review, even when non-Docker items are also marked. A failed or skipped trim never undoes removals.
2. **How the trim runs: our own small image. [User]** (pulls are allowed; building our own image is the user's preferred route if it is better, and it is). The app builds one image, `maccleanup/vm-tools`, from a Dockerfile piped through stdin (`docker build -t maccleanup/vm-tools -`; no file on disk), `FROM` a pinned `alpine:3.x` tag (pulled if missing, which is allowed), labelled `com.maccleanup=1`, with the entrypoint `nsenter -t 1 -m -u -n -i fstrim -v /var/lib/docker`. It replaces the 2019 `docker/desktop-reclaim-space` image, which is not run any more. Tested on 2026-11-06 on this Mac: a 12.9 MB image, built from the local alpine with no pull, ran for 2 s with exit 0 and printed `fstrim -v`'s line. The image is also the browsing helper (item 8), so one image serves both jobs. The app lists it in the Docker page's image section (marked as ours, never offered for bulk marks) and rebuilds it when its Dockerfile text changes (a content label carries the version). The trim runs in the Docker VM, not as an admin on the Mac. If the trim reports success but the file did not shrink, the feature still reports the measured result as it is (including zero); it is not treated as an error. The number `fstrim -v` prints is the size of the free range it asked the disk to discard, not what the file shrank by (it printed 425.6 GiB on a 32 GB file), so it is never shown as a result.
3. **What "truly freed" counts.** The Mac volume's free-space delta stays the truth (parent rule). The `Docker.raw` allocated-size change is shown next to it, never added to it. A zero or negative change is shown as is. Local snapshots holding the blocks show up through the existing snapshot accounting.
4. **`Docker.raw` is protected from file deletion.** `Docker.raw` and the Docker Desktop data folder are refused by `Policy` in the Explorer and on the Caches page (shown red, with a note pointing to the Docker page); a test pins this. The Docker page's totals line counts them from Docker's own numbers and the `du` of the file, not from the scan.
5. **Dates in the Explorer and Caches pages.** To keep the consistency rule, the Explorer and the Caches & Projects page get a Modified column (the newest modification time inside a folder, kept as an additive per-folder counter during the scan so the hot path stays lock-free). The Docker page shows Last used and Created. The two sets of date columns are laid out the same way and sorted in header order. This is the largest cross-cutting change and the user should confirm it, see the hand-over note.
6. **Removal order and dependencies.** Containers are removed first, then images, then volumes. An image with stopped containers cannot be removed unless those containers are marked as well: the review lists the problem and refuses `y` until the user marks them or unmarks the image. A removal Docker refuses anyway is reported on the finish screen and the rest continue.
7. **Context.** Every Docker command pins the local Docker Desktop context (`desktop-linux`) explicitly; if it is not there, the page says "Docker Desktop not found" and offers nothing to run. Nothing ever runs on another context.
8. **Browsing helper.** The helper is a container of our own `maccleanup/vm-tools` image (item 2) with the volume mounted read-only and no network, overriding the entrypoint to list files, and removed afterwards. If the image cannot be built or the base cannot be pulled, browsing says why. Images and containers are browsed from a container that is created and never started.
9. **Smaller points.** First parent for the tree is the first by name in a fixed order. The list refreshes on entering the page, after a cleanup and on `r`, never on a timer. A stopped daemon shows "Docker is not running" with `r` to retry.

## 10. As built (2026-11-07)

**Where this section differs from sections 1 to 9, this section wins.** Choices are **[My call]** unless marked **[User]**.

- **Data source.** Docker is read from the Engine API over the Docker Desktop unix socket with `curl` (through `CommandRunner`), not from CLI JSON: the CLI prints rounded sizes (`17.3GB`) and no build-step commands for cache records, the API gives exact bytes, `Description`, `LastUsedAt`, `UsageCount` and the `" Parents"` key (Docker really spells it with a leading space). Removals and the helper image still use the `docker` CLI.
- **Helper image [User].** `maccleanup/vm-tools` is built from a Dockerfile on stdin `FROM busybox:musl` (2.5 MB, official; alpine was 3.9 MB), labelled `com.maccleanup=1` and `com.maccleanup.version=2`, with no `RUN` step (busybox has `sh`, `du`, `stat`, `nsenter`, `fstrim`), so building needs no package download. It trims the VM disk and lists volumes.
- **Browsing.** Volumes and images only. Containers are not browsable (a stopped one cannot be listed without starting it, a running one only by `exec`). Both listings use one portable shell script (`vmtools::LIST_SCRIPT`): `du -sk` gives a folder the total of everything inside (like the Explorer), `stat -c` gives sizes and times, records end with NUL. A volume runs it from the helper (mounted `:ro`, `--network none`); an image runs only its own `sh` with the script (`--network none --read-only`), so an image without a shell cannot be browsed. `b` opens it, and `Enter` on an image or volume with nothing to unfold does too. **[User]** asked for sizes, dates and folder totals.
- **The file browser looks like the Explorer [User]:** columns Name, Size, Modified (sorted column white with an arrow, `s` walks them in header order, default biggest first, folders sort with the rest), a share bar when there is room, the graph at the side (`t`, `[`, `]`, clickable), filter and scrollbar. The grey for borders, headers and hints (`ui::DIM`) is a fixed light grey (`Rgb(170, 176, 192)`), not the terminal's dark gray, which is hard to read on dark themes **[User]**.
- **Build cache** is a flat list (sortable by size or last used); what a record was built on is shown in the details.
- **Removing.** Tagged images are removed by their tag(s) (readable in the review; an id with several tags is refused by Docker unless forced), dangling ones by id. Build-cache records are removed with `docker builder prune -f --filter id=<id>`; **this was not verified against a real Docker** (the auto-mode safety check blocked the one real test, because a misbehaving filter could clear the whole cache), so the first real use should be on a record you do not mind losing. The review shows the whole command (no `--context` flag, long ids shortened to 12 characters for display only).
- **Trim.** A `VM DISK` section with one `Shrink VM disk` row (its Frees is an upper bound, `≤`). Marking any removal adds it (unmark it to skip; marking the row yourself runs it alone). The finish screen reports `Docker.raw`'s allocated size before and after, including zero.
- **Dates.** The Explorer and Caches & Projects got a **Modified** column **[User]** (newest file inside a folder, kept as an additive counter by the scan, so a rescan after deletions can leave it slightly high); Docker has Last used (a `~` marks a value worked out from containers) and Created. Optional columns give way before names do: Share, then Modified (Explorer-like screens); Share, then Created, then Last used (Docker).
- **Details pane [User].** Shows the whole command of a layer or build step, wrapped; `J` / `K` scroll it when it does not fit.
- **Real check (2026-11-07), only my own throwaway image.** A 60 MB image (`maccleanup-throwaway:test`, 128 MB as Docker counts it) was removed through the real app: the review named exactly that one image and the trim; the run took a few seconds; `Docker.raw` went from 33,442,784 KB to 33,381,424 KB on disk (about 61 MB back), the finish screen said "shrank by 62.8 MB" and "freed 60.6 MB this session". Its build-cache record (126 MB) was left in place (see above); the `fstrim -v` figure (hundreds of MiB) is the range it asked the disk to discard, not a result, and is never shown.
- **Known minors.** The finish list still shows each command with its `--context` flag; the fuzzy filter matches long layer commands loosely (use `'exact` terms to narrow); the Docker page reads on entering, on `r` and after a cleanup, never on a timer.
